A 70B-parameter model in BF16 is **140 GB** of weights. That needs at least two 80 GB GPUs before you store a single token of [KV cache](../kv-cache/). Every decode step also has to stream all 140 GB through the memory bus. **Quantization** stores the numbers in fewer bits, so the model shrinks, the bus moves fewer bytes per token, and on modern GPUs the math itself can run faster.

## Bits, exponents and mantissas

A floating-point number spends its bits on three things: a **sign**, an **exponent** that sets the *range* (how big or small a value can be), and a **mantissa** that sets the *precision* (how finely values are spaced). Integers have no exponent: they are evenly spaced and need an external **scale** to map them onto real values.

| **FP4 E2M1** | 1 / 2 / 1 | 6 (× block scale) | NVFP4 (NVIDIA Blackwell and later) / MXFP4 (Blackwell, AMD MI355X) |

## Scales, granularity and outliers

To quantize a tensor $w$ to a $b$-bit integer, pick a scale $s$ and round:

$$
q = \mathrm{round}\!\left(\frac{w}{s}\right), \qquad s = \frac{\max |w|}{2^{b-1} - 1}, \qquad \hat w = q \cdot s
$$

The **absmax** sets the scale, so a single big value stretches the grid for everything that shares that scale, and small values round to zero. The fix is to use **more scales over smaller groups**. One scale per tensor is crude. One per output channel is common for 8-bit. One per **group of 32–128 weights** is standard for 4-bit.

<Callout type="tip" title="Activations are worse than weights">
Weights are fixed and fairly well-behaved, so you can calibrate them offline. **Activations** change with every input, and LLMs develop a few hidden-state channels with values 100× larger than the rest. That is why 8-bit *activation* quantization needed tricks like **SmoothQuant**, which moves part of the outlier magnitude from activations into the weights with a per-channel rescale. FP8's exponent helps here too: it tolerates a wide dynamic range far better than INT8.
</Callout>

## Getting from FP16 to 4 bits without breaking the model

Rounding every weight to its nearest grid point (**round-to-nearest**, RTN) works at 8 bits and starts to hurt at 4 bits. The popular post-training methods are smarter about it:

- **GPTQ** quantizes weights one column at a time and updates the not-yet-quantized columns to **compensate** for the error, using second-order information from a small calibration set.
- **AWQ** observes that ~1% of weight channels matter most, namely those that see large activations. It **scales those channels up** before quantizing so they keep more precision.
- **GGUF** (llama.cpp) packs block-quantized formats like Q4_K and Q8_0 into a single file for CPU, Apple silicon and edge inference.
- **Microscaling** puts the scales into the hardware format itself, and the tensor cores apply them natively. **MXFP4** (the OCP standard) gives each block of 32 FP4 values a power-of-two E8M0 scale. **NVFP4** uses blocks of 16 with an FP8 E4M3 scale, plus one FP32 scale per tensor: finer steps and better accuracy, at 0.5 bits per weight of overhead. A checkpoint made for one format is not automatically fast on hardware built for the other.

## Which phase gets faster?

This is the most important practical question, and the answer depends on whether the **math** runs in low precision or only the **storage** does.

- **Weight-only (W4A16, W8A16)**: weights are stored small and **dequantized to BF16 inside the kernel**. That cuts the bytes read per token, which is exactly what memory-bound [decode](../prefill-decode/) needs. The math still runs in BF16, so compute-bound **prefill gains little**, and at large batch the dequantization overhead can even make it slower.
- **Weight + activation (W8A8 FP8/INT8, W4A4 FP4)**: both operands are low-precision, so the **tensor cores run at 2× (8-bit) or 4× (4-bit) the BF16 rate**. That speeds up prefill *and* large-batch decode. It needs hardware support: FP8 on NVIDIA Ada, Hopper and newer and on AMD MI300 and newer; FP4 on NVIDIA Blackwell and AMD MI355X. The [hardware page](../hardware/) lists every chip's formats.

<Callout type="warn" title="4-bit can make you slower under load">
A team switches from FP8 to INT4 weight-only to "save GPUs", and throughput under load **drops**. At large batch, decode is no longer purely memory-bound, and the INT4 kernel pays dequantization costs and runs BF16 math. The FP8 kernel was using native low-precision tensor cores. Always benchmark at your real concurrency.
</Callout>

## Don't forget the KV cache

Quantization is not just for weights. An **FP8 KV cache** halves the cache's memory per token, so you can fit roughly twice the concurrent sequences or context length. Decode also reads half as many cache bytes. The per-token scales can be per tensor or per head. The risk is **long-context accuracy**: attention over thousands of slightly perturbed keys can blur exact recall. Use the [KV calculator](../kv-cache/) to see the capacity gain, and evaluate retrieval-heavy tasks before you turn it on.

## Proving it's good enough

1. Compare against the BF16 model on **your own task evals**, with identical prompts and sampling settings.
2. Include the slices most likely to regress: **math and reasoning, code, long context, structured output and tool calls**, and non-English languages.
3. Watch **output length** too. Quantized models sometimes ramble or stop early, which shifts cost and latency.
4. Set acceptance thresholds **before** running the evals, and keep the BF16 model deployable for rollback.

<Interview>
  <Q q="What do the exponent and mantissa bits control in a float format?" level="core">
    The exponent sets the **dynamic range**, from the smallest to the largest representable magnitude. The mantissa sets the **precision**: the relative spacing between neighbouring values. BF16 keeps FP32's 8 exponent bits (same range) and keeps only 7 mantissa bits. FP16 has more precision (10 bits) but overflows above 65,504.
  </Q>
  <Q q="Weight-only INT4 vs W8A8 FP8: which phase does each speed up?" level="core">
    W4A16 cuts bytes read, so it speeds up memory-bound **decode** at small batch, but the math is still BF16, so **prefill** barely improves. FP8 W8A8 runs the matmuls on FP8 tensor cores at about 2× the BF16 rate, so it speeds up **prefill and large-batch decode**, as long as the GPU supports FP8.
  </Q>
  <Q q="Why do we use per-group scales for 4-bit weights?" level="mid">
    With only 16 levels, one large value in a group stretches the step size and rounds small weights to zero. Smaller groups (e.g. 128 weights) adapt the scale to local magnitudes. The overhead is one FP16 scale per 128 weights, about 0.125 extra bits per weight.
  </Q>
  <Q q="What problem does SmoothQuant solve?" level="mid">
    LLM activations have a few outlier channels that make per-tensor INT8 activation quantization very lossy. SmoothQuant divides those activation channels by a per-channel factor and multiplies the matching weight rows by the same factor. The math is unchanged, but the activations become easy to quantize and the weights absorb the difficulty.
  </Q>
  <Q q="We moved to INT4 to save GPUs and throughput at peak load dropped. Why?" level="senior">
    At high concurrency, decode becomes more compute-bound. The W4A16 kernel dequantizes in registers and does BF16 math, so it loses to FP8 W8A8, which uses native FP8 tensor cores. Check which kernel was selected, measure throughput at several concurrency levels, and compare output lengths and any changed engine flags (e.g. speculative decoding settings).
  </Q>
  <Q q="How do NVFP4 / MXFP4 differ from INT4 with group scales?" level="senior">
    They are **floating-point** 4-bit values (E2M1) with a shared per-block scale (8-bit) applied natively by the tensor cores. That makes W4A4 matmuls possible at 4-bit throughput. INT4 group quantization is usually weight-only and dequantized to BF16 before the math. FP4 needs Blackwell-class hardware and careful accuracy validation.
  </Q>
</Interview>
